# WAF 载荷变异与探测指南

工具箱 → **WAF 变异**。三个区块，从「看清楚」到「试一下」：

| 区块 | 发请求吗 | 用来干什么 |
|---|---|---|
| ① 认 WAF | 否 | 把你已抓到的响应贴进来，按特征比对是哪种 WAF |
| ② 载荷变异 | 否 | 一条载荷的 15 种等价写法，挑一个 |
| ③ 主动探测 | **是** | 分批发出去，比对响应，看哪条没被拦 |

---

## ① 认一下是什么 WAF

把**你已经抓到的**响应头或拦截页片段贴进去，点「比对」。

它拿 12 类常见 WAF 的特征做文本匹配（Cloudflare、AWS WAF、Akamai、阿里云、腾讯云、ModSecurity、F5、Imperva、Sucuri、FortiWeb、安全狗、D盾）。

这一步**不发任何请求**——它只看你手上的数据。识别出名字后，点一下那个名字即可套用针对性的变异组合。

## ② 载荷变异

输入一条载荷（比如 `1' OR '1'='1`），勾选想要的技术，点「生成」。

15 种技术：

| 技术 | 做什么 | 针对 |
|---|---|---|
| URL 编码 | 空格等转 `%XX` | 按原文匹配的规则 |
| 双重 URL 编码 | `%` 也编码成 `%25` | 只解码一次的 WAF |
| Unicode 编码 | 转 `\uXXXX` | 不处理 Unicode 的解析链 |
| 大小写混用 | `SeLeCt` | 区分大小写的正则 |
| 注释分割 | `/ ** /` 替空白 | SQL 里等价于空格 |
| 内联注释包裹 | `/*!50000select*/` | MySQL 会执行注释内容 |
| 空白替换 | 空格换 `%09` `%0a` `%0c` `+` | 只过滤空格的规则 |
| 关键字双写 | `oorr` → `or` | 只替换一次的过滤器 |
| 等价关键字 | `and`→`&&`、`or`→`||` | 关键字黑名单 |
| 引号变形 | `'` / `"` / 反引号互换 | 引号规则 |
| 字符串拼接 | `'a'||'b'` | 整串字面量匹配 |
| 换行注入 | 关键字中间插换行 / `%0d%0a` | 单行匹配 |
| 分块编码 | HTTP chunked 形式 | 分块处理不当的网关 |
| 参数污染 HPP | 同名参数重复 | 前后端取值不一致 |
| Base64 / hex 包装 | 整体编码 / `0x...` | WAF 之后才解码的场景 |

结果逐条可点即复制。

## ③ 主动探测（会真的发请求）

这是唯一会向外发请求的部分，**必须先勾选授权**。

### 怎么用

1. 在你想注入的位置写 `{{PAYLOAD}}` 占位符。URL、请求头、请求体都可以，而且可以多处：
   ```
   URL:  https://target.example.com/search?q={{PAYLOAD}}
   头:   User-Agent: {{PAYLOAD}}
   体:   {"q":"{{PAYLOAD}}"}
   ```
2. 选方法（GET / POST / PUT）。
3. 在 ② 勾选要试的技术（① 里识别出 WAF 后点一下名字，会替你勾好针对性的组合）。
4. 勾选授权，点「开始探测」。

### 它做什么

- 先发一条**基线**：原始载荷，拿到参照响应 —— 基线**只在第一批**发一次，后面每批沿用同一条；
- 再**按批**发变异载荷，批内**串行**，每条之间停 300ms；
- 一批发完就**停下来**，界面出现「**继续下一批（剩 N）**」，发不发由你决定；
- 每条与基线比对，给出判定。

### 判定怎么看

| 判定 | 含义 |
|---|---|
| 基线 | 原始载荷的响应，只作参照 |
| **疑似绕过** | 状态码与响应长度都和基线一致 —— 值得人工确认 |
| 被拦截 | 状态码命中拦截码（403/406/418/419/429/501/999），或响应体命中拦截特征词 |
| 响应有变化 | 和基线不一样但不像拦截，可能被改写了，自己看一眼 |
| 请求失败 | 连不上、超时、URL 不合法 |

「疑似绕过」只是一条**线索**，不等于漏洞成立 —— 最终要你自己看响应内容再判断。

### 分批探测：一次一批，不会一口气全发

探测天生是"发很多条"，一口气全甩出去既可能把目标打崩、也容易失控。所以做成**队列**：

- 开始探测时，所有变异载荷进队列，**只发第一批**（每批上限默认 200 条，见下面的「高级设置」）；
- 界面上显示「**继续下一批（剩 123）**」，点一次发下一批，直到队列空了按钮消失；
- **基线只在第一批发** —— 后面每批仍然跟同一条基线比，不重复发基线；
- 中途「停止」：已发的结果保留，队列丢掉。

> 每批之间是断开的，你有充足机会看一眼结果，再决定要不要继续。

### 高级设置（间隔 / 超时 / 单次上限）

点 ③ 右上角的「**高级设置**」，三个滑块：

| 项 | 默认 | 范围 | 说明 |
|---|---|---|---|
| 请求间隔 | 300ms | **100ms** ~ 5000ms | 两条之间的等待 |
| 单条超时 | 15s | 3s ~ 60s | 单条请求多久算超时 |
| 单次上限（每批条数） | 200 条 | 10 ~ **2000** 条 | 一批最多发多少 |

有两条**改不动的底线**：间隔不低于 **100ms**、总量不超过 **2000 条**。
再往上调会直接把目标打崩或把本机拖死，所以封死。设置会记住。

### 边界（刻意不做的）

- 不内置攻击载荷字典，不做载荷的组合搜索/爆破；
- 不并发：串行发送 + 固定间隔，按批推进（默认每批 200 条，由你手动续批）；
- 两条硬底线改不动：间隔 ≥ 100ms、总量 ≤ 2000 条；
- 不自动利用、不自动提取数据、不做反溯源 / 代理轮换；
- 判定只陈述事实（状态码 / 长度 / 特征词），不打「漏洞」「高危」这类标签。

### 授权

只对你**拥有**或**已获书面授权**的目标使用。未经授权尝试绕过他人系统的防护措施，在很多司法辖区是违法的。

## 常见问题

**Q：探测全是「被拦截」怎么办？**
说明目标 WAF 对这些写法都认得。可以只换一项技术重试，或者结合 ① 的识别结果套用针对性组合。

**Q：探测全是「请求失败」？**
先检查 URL 能不能通（用工具箱的 HTTP 请求构造或直接 curl）。探测走的是本机网络，**不经过 ProxyPin 自身的代理**。

**Q：想从已抓到的请求直接发起探测？**
在 ③ 里手动填 URL / 头 / 体即可 —— 把抓包详情里的内容贴过来，在要注入的位置替换成 `{{PAYLOAD}}`。

**Q：为什么发了一批就停了？**
A：这是**分批**设计 —— 一次最多发一批（默认 200 条），发完停下来让你看结果；
要接着发就点「继续下一批（剩 N）」。不会一口气把所有载荷甩出去。

**Q：间隔 / 上限能调吗？**
A：能，点 ③ 的「高级设置」。但间隔最低 100ms、总量最高 2000 条这两条底线封死了，调不动。

**Q：为什么结果里技术比我勾的少？**
有些技术对特定载荷不产生改变（比如载荷里没有空格，空白替换就无从下手），这类不会发出去浪费请求。
