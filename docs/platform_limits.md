# 平台与技术边界说明

> 有些"功能请求"不是没做，而是在当前技术路线下**做不到**，或者需要付出与收益明显不匹配的代价。
> 这篇把最常见的三类讲透：Mac App Store 应用、鸿蒙、QUIC 完整解密。

---

## 一、Mac App Store 应用抓不到（上游 #874）

**现象**：从 App Store 安装的应用，即使系统代理已指向 ProxyPin、根证书也装好了，流量依然不出现在抓包列表里。

**原因**：

- **App Sandbox 强制开启**：沙箱应用的出网请求由系统在沙箱容器内代理，**不读取用户级的系统代理设置**；
- 应用被**强制签名与公证**：向进程内注入、劫持其网络栈会破坏签名，进程直接拒绝运行。

**为什么不做"半成品"方案**：macOS 理论上可以用 `pf` 的 `rdr` 规则把 80/443 流量重定向到本地代理端口（类似 Linux 的 iptables REDIRECT），但——

1. 需要 root 权限并常驻 `pf` 规则，**规则配错会直接断网**；
2. 重定向后必须还原"原始目标地址"，否则代理不知道该连哪里；
3. 与系统代理、VPN 并存时冲突面大，用户很难自己排错。

这类接管应当由**带签名的 Network Extension（NETransparentProxyProvider）**完成，而本仓是未签名构建，无法分发此类扩展。

**可用替代**：

- 用同一个应用的**非商店版本**（官网 / dmg / Homebrew 安装的版本会读系统代理）；
- 把 ProxyPin 作为**上游代理**，交给支持 TUN 的工具统一接管；
- 只是要看某个 iOS 应用时，用 iOS 版 ProxyPin——iOS 侧是 VPN 通道（NEPacketTunnelProvider），不受 App Sandbox 那套系统代理限制的约束。

## 二、鸿蒙（HarmonyOS）暂未提供构建（上游 #683）

**要具备什么**：

- Flutter 的 **ohos 分支工具链** + DevEco Studio（与官方 stable 不同源）；
- 独立的 `ohos/` 工程（ArkTS 壳、模块配置、签名配置）；
- 平台能力适配：VPN 通道（HarmonyOS 的 VpnExtension 与 Android 的 VpnService 接口不同）、证书安装引导、文件选择器等；
- 一套独立的 CI——鸿蒙构建与签名无法复用现有 Android 流程。

这是一次**独立移植**，不是"加一个构建目标"，且需要长期维护第二套移动端代码。当前未做，欢迎社区按上述清单贡献。

**替代**：在鸿蒙设备上把 WLAN 代理指向另一台设备（Android / iOS / 电脑）上的 ProxyPin。

## 三、QUIC / HTTP3 为什么无法"完整解密"（上游 #489）

**一个常见误解**：TCP + TLS 场景下我们能解密，是因为我们是**主动的中间人**——自己给对方签证书、自己完成两次 TLS 握手，因此**握着会话密钥**。QUIC 的场景不同：VPN 层只是把 UDP 包**旁路抄送**给应用，我们没有参与握手，也没有任何一方的私钥。

**关键在 ECDHE**：TLS 1.3 的会话密钥由客户端与服务端通过 ECDHE（临时椭圆曲线密钥交换）协商——双方各自生成临时私钥、交换公钥、各自算出共享密钥。只拿到密文和双方公钥**无法推导共享密钥**（椭圆曲线离散对数问题）。所以即使能看到 100% 的 QUIC 包，也解不开 1-RTT 应用数据。

**我们已经做到的**：

- 解析 QUIC Initial 包（规范设计上它用公开可派生的密钥加密），提取 **SNI 域名**、版本、连接 ID，统计包 / 帧 / 流量，并以会话列表与**时间轴**呈现；
- 提供「拦截 QUIC」开关：丢弃 UDP:443 让应用回落 TCP HTTP，**内容即可正常抓取**（Charles 同款方案）；
- **导入密钥日志解密 1-RTT**（本版落地）：拿到目标应用导出的密钥日志后，QUIC 连接页右上角「钥匙」导入即可解密命中连接的客户端方向应用数据。

**为什么"导入密钥日志"才是正解**：密钥由客户端与服务端通过 ECDHE 协商，被动旁路拿不到；但**应用自己**在握手时知道会话密钥，把它导出成 NSS key log（`SSLKEYLOGFILE` 格式）后，我们就能用 `*_TRAFFIC_SECRET_0` 反推 1-RTT 密钥。浏览器可加启动参数导出（如 Chrome 的 `--ssl-key-log-file`），普通 App 默认不会——所以这是"**能拿到就解、拿不到不强求**"的能力。

**解到什么程度**：解到 **QUIC 流数据层**——去掉头部保护、AEAD 解密、解析帧，取出 STREAM 数据并给出可读预览；并进一步对 **HTTP/3 HEADERS 帧做 QPACK 解码**（v1.22.79：简化子集——99 项静态表 + Huffman），流预览里能直接看到 `:method` / `:path` / `content-type` 等头部（**动态表**引用以 `:dynamic-*` 占位标出，未纳入）（判断"哪个域名在传什么内容"已足够，要看完整明文请求仍推荐开「拦截 QUIC」回落 TCP）。

## 四、遇到别的"抓不到"

先跑一遍工具箱里的**抓包自检**（或让 AI 通过 MCP 工具 `diagnose_capture` 读结论），它会检查代理服务、系统代理、CA 证书、最近流量，并按常见原因给出建议。
