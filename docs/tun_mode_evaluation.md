# TUN 模式可行性评估

> 针对上游 #896「Windows 下无法抓到某些进程的包」一类的需求，评估用 TUN（三层接管）替代/补充
> 现有「系统代理 + WinHTTP」方案的技术可行性与成本。结论先行：**技术可行，但成本极高，
> 瓶颈不在 TUN 本身，而在桌面端的 IP 协议栈**——建议优先级为低，除非有明确的用户诉求。

## 1. 现状：不同平台差得很远

| 平台 | 现在怎么接管流量 | 是否需要 TUN 模式 |
| --- | --- | --- |
| Android | `VpnService` + 自研 TCP/UDP 栈（`vpn/transport/protocol/*.kt`） | 不需要，已经是三层接管 |
| iOS | `NEPacketTunnelProvider` + 自研栈（`ios/ProxyPin/vpn/**`） | 不需要，同上 |
| Windows | 系统代理（WinINET）+ WinHTTP 接管（`netsh winhttp set proxy`）+ 环境变量 | 部分进程抓不到 → 想要 |
| macOS | 系统代理（`networksetup`） | 少数非合作进程 → 可选 |
| Linux | 系统代理 + `http_proxy` 环境变量 | 同上 |

也就是说：**移动端早就做到"接管 IP 层"了，桌面端没有**。用户报的"某些进程抓不到"，本质是那些
进程压根不看系统代理设置（自己实现网络栈、或是服务进程）。

## 2. TUN 本身：三个平台都不难

| 平台 | 需要什么 | 权限 | 说明 |
| --- | --- | --- | --- |
| Windows | `wintun.dll`（WireGuard 项目，微软签名，用户态加载，**不需要装驱动服务**） | 管理员 | Dart 可用 `dart:ffi` 直接调用；创建适配器 + 配 IP/MTU + 加路由 |
| macOS | 系统自带 `utun`（无需第三方驱动） | root | 项目已有提权机制（`osascript ... with administrator privileges`，见 `system_proxy.dart`） |
| Linux | `/dev/net/tun`（内核自带） | root / `CAP_NET_ADMIN` | 可用 `pkexec` 提权（证书安装已这么做） |

路由建议用「`0.0.0.0/1` + `128.0.0.0/1`」两条明细路由覆盖默认路由，而不是直接改默认网关——
这样退出时只需删掉自己加的两条，不影响用户原有网络配置。

**TUN 部分本身大约是每平台几百行的量级，不构成主要障碍。**

## 3. 真正的瓶颈：桌面端没有 IP 协议栈

从 TUN 读出来的是**原始 IP 包**，要变成可抓可改的 HTTP 流量，需要一整套：

- IPv4/IPv6 头解析、分片处理
- TCP 状态机（三次握手、序号/确认、重传、窗口、四次挥手）
- UDP + DNS 处理
- 与现有 HTTP 代理核心对接（把"一条 TCP 流"交给既有的 MITM/转发逻辑）

而 Android 版是 **Kotlin**、iOS 版是 **Swift**，桌面端是 **Dart** —— **现有栈无法直接复用**，
必须重写一份。工作量估计：

- 最小可用（只处理 IPv4 + TCP 80/443，不碰 UDP）：**1500~2500 行**，且大量边界情况要真机调
- 完整（含 UDP/QUIC、IPv6）：**4000 行以上**，接近"再造一个移动端协议栈"

可选实现路径：

1. **纯 Dart 实现** —— 与现有代码同语言、便于维护；性能到几十 Mbps 量级，抓包够用。
2. **Rust 库 + FFI** —— 性能与复用性最好，但需要引入新的构建链路（跨三平台编译）。

## 4. 风险清单

- **断网风险**：路由或 DNS 配错会让整机失去网络。必须照搬 Root 模式那套安全网——
  只在用户显式开启时执行、退出时按相反顺序清理、App 启动时清理上次残留。
- **杀软误报**：创建虚拟网卡 + 改路由在 Windows 上是"网络接管"行为，容易被安全软件拦。
- **权限门槛**：Windows 要管理员、macOS/Linux 要 root——这比"系统代理"高一个台阶，需要清晰的引导。
- **与现有系统代理冲突**：同时开系统代理 + TUN 会绕圈，必须互斥（同 Root 模式的处理）。

## 5. 性价比更高的替代方案

在动 TUN 之前，这些手段的成本低一个数量级：

1. **已有的 WinHTTP 接管**（`windows_takeover.dart`）已覆盖大量服务类进程，先确认它默认是否开启。
2. **引导目标程序自己设代理**：不少客户端（下载器、部分 IDE、部分游戏启动器）提供代理设置项，
   文档里给一份清单比写 2000 行协议栈划算。
3. **进程级注入（Detours / WFP 重定向）**：能覆盖"不走系统代理"的进程，但需要注入 DLL，
   杀软误报更严重，且属于"修改其他进程"的高风险行为——不建议。
4. **明确告知边界**：在抓包自检页写明"哪些进程抓不到、为什么、有哪些替代手段"，
   比让用户反复试错体验好。

## 6. 建议

- **优先级：低。** 收益是覆盖少数"完全不合作"的进程；代价是一套跨平台协议栈 + 断网风险 + 权限门槛。
- 如果要做，建议按这个顺序推进：
  1. 先只做 **Windows + 仅 TCP 80/443 + IPv4**，把"TUN 读取 → TCP 流 → 复用现有 HTTP 转发"这条链路跑通；
  2. 把安全网（显式开启、退出清理、启动清理残留、与系统代理互斥）做成和 Root 模式一样的规范；
  3. 再考虑 UDP/DNS（这一步才需要处理 QUIC 那类问题）。
- 在决定做之前，建议先收集真实诉求：**到底有多少用户属于"目标进程完全不看系统代理"**。
